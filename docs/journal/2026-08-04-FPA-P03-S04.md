# FPA-P03-S04 — PostgreSQL row-level security

**Date:** 2026-08-04

**Status:** Completed and approved

**ADR:** ADR-0005 §9

## Scope

This stage adds PostgreSQL defense-in-depth for Family Space tenancy. It does
not add deletion/audit workflows from S05 or create a speculative domain table.

## Implementation

- Added a separately provisioned `fambam_app` runtime role with
  `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOINHERIT` and `NOBYPASSRLS`.
  Compose uses owner credentials only for migrations and runtime credentials
  for the API server.
- Added transaction-local database request context. User identity is set after
  authentication; Family Space identity is set only after active-membership
  resolution or inside the bounded creation and invitation-acceptance flows.
- Enabled and forced RLS on `family_spaces` and
  `family_space_memberships`, with distinct registry and access-control
  policies matching ADR-0005.
- Defined the ordinary tenant-table policy anchor through
  `app_current_family_space_id()` and documented the required `USING` plus
  `WITH CHECK` pattern. Because the production schema does not yet contain an
  ordinary tenant-owned content table, the PostgreSQL suite creates and drops a
  focused integration fixture rather than adding speculative product schema.
- Preserved atomic Family Space creation and membership reactivation during
  invitation acceptance by establishing authoritative transaction-local tenant
  context inside those services.

## PostgreSQL verification

`make test-api-postgres-rls` provisions a disposable PostgreSQL 17.6 database,
runs all migrations as the owner, connects the tests as the runtime role, and
automatically removes the container. Its coverage includes:

- non-superuser/non-`BYPASSRLS` runtime attributes and `FORCE RLS`;
- registry-to-membership resolution against PostgreSQL's real policy evaluator,
  including absence of recursive-policy errors;
- self-only membership visibility before tenant resolution;
- tenant-scoped membership administration;
- missing-context and cross-tenant Class C read/write rejection;
- `WITH CHECK` rejection of cross-tenant inserts and tenant reassignment;
- transaction context cleanup after commit and rollback;
- atomic Family Space creation, successful removed-member reactivation and
  rollback of rejected acceptance for an already-active member.

Focused result before full repository verification: 7 tests passed with 49
assertions.

## Persistent local migration verification

After explicit approval, Compose provisioned the restricted role, applied the
S04 migration as batch 7 through the short-lived `api-migrate` service and
rebuilt the API and web services. Verification established:

- `fambam_app` is the live API connection role and is not a superuser, cannot
  create databases or roles, does not inherit privileges and cannot bypass RLS;
- both protected tables have RLS enabled and forced, with all seven expected
  policies installed;
- the existing Family Space, both memberships, active Owner and invitation
  Family Space associations were preserved;
- without database context, the runtime connection sees zero Family Spaces and
  zero memberships; with the first user's context it sees one Family Space and
  one self-membership;
- both database settings return `NULL` after the transaction completes;
- the runtime role has no hard-delete privilege on `family_spaces` and no
  access to Laravel's migration ledger;
- API health returned 200, an unauthenticated scoped route returned 401 and the
  frontend tenant route returned 200;
- infrastructure and observability smoke checks passed against the rebuilt
  RLS-enabled stack. The migration-ledger smoke check now correctly runs through
  the short-lived migration service rather than broadening runtime privileges.
