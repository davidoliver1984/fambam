# FPA-P08-S02 — Exact duplicate detection

## Outcome

Exact duplicate detection now assists both Photo-creation paths without
deleting uploads, inventing a canonical Photo, broadening authority or exposing
invisible family content. Existing Photo conversation history is preserved
honestly while all new comments and reactions use an Album context.

## Implementation

- Compared the frozen `MediaUpload.original_sha256` only within one Family
  Space and disclosed only matching Photos already visible to the actor.
- Added the three explicit direct-creation outcomes: use the selected existing
  Photo, create an independent Photo, or cancel.
- Paused asynchronous Album/Event contribution on a separate
  `MediaUploadDuplicateHold`, visible and resolvable only by the original
  uploader while they retain the same live contribution authority.
- Carried the exact disclosed candidate identifiers into create-new resolution,
  revalidated them and atomically recorded one canonical `DuplicateDecision`
  per disclosed match. Newly appearing or undisclosed matches are never
  recorded as though the actor reviewed them.
- Added idempotent retrospective exact candidates and settled-decision
  suppression, without introducing any perceptual matching.
- Added nullable Album scope to comments and reactions. New writes always name
  a current AlbumPhoto context; legacy null-Album rows are direct-page-only and
  read-only; removing and re-adding an AlbumPhoto retains its prior conversation.
- Added feature-local typed API functions, TanStack Query hooks and duplicate
  choice components, including explicit visibility-widening confirmation when
  an existing private Photo is added to a broader Album.

## Architecture

No accepted ADR text required correction. The work is exact-checksum-only and
does not introduce perceptual hashing, merging, redirects, content aggregation,
automatic deletion, or a new MediaUpload lifecycle state.
