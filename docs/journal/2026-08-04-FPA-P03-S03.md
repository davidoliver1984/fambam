# Session 2026-08-04 — FPA-P03-S03

## Session objective

Implement ADR-0005's friendly Family Space route resolution, request-scoped
tenant context, role policies and explicit tenant query scoping without pulling
PostgreSQL row-level security or deletion lifecycle work forward from later
Phase 3 stages.

## Active scope

- Resolve `/families/{slug}/...` only through the authenticated user's active
  membership, with unknown and inaccessible slugs returning the same 404.
- Bind and clear one request-scoped tenant context after successful resolution.
- Apply policies to role-sensitive Family Space actions.
- Resolve nested membership and invitation records explicitly within the active
  Family Space rather than through global route-model binding.
- Make the frontend's active Family Space URL-derived with tenant-aware query
  keys and protected routes.

## Explicitly deferred

- PostgreSQL roles, session settings, RLS policies and circular-policy
  verification belong to FPA-P03-S04.
- The deletion state machine, asynchronous tenant propagation and remaining
  tenancy audit/deletion surfaces belong to FPA-P03-S05.

## Work completed

- Added a request-scoped `TenantContext`, resolved only after one explicit
  Family Space query proves the authenticated user's active membership, and
  cleared it in middleware `finally` handling after every scoped request.
- Ordered Family Space resolution ahead of Laravel's implicit binding so the
  public slug is never treated as a globally resolved model identifier.
- Added explicit query classes for accessible Family Spaces, tenant-scoped
  memberships and tenant-scoped invitations. Nested identifiers are resolved
  only inside the active Family Space.
- Added a Family Space policy for space access, invitation administration and
  membership administration; application-level Owner rules remain enforced by
  the existing domain service after policy authorization.
- Replaced global invitation-management endpoints with
  `/api/families/{slug}/...` routes and added scoped membership-management
  routes.
- Introduced the first protected React Router boundary using the audit-clean
  direct `react-router` 8.3.0 package. The active Family Space is derived from
  `/families/:familySlug`; tenant reads and invitation queries use slug-aware
  TanStack Query keys and feature API modules.
- Kept Family Space creation and invitation acceptance outside ordinary slug
  resolution, as required by ADR-0005's independently authoritative identifier
  flows.
- A rebuilt-stack HTTP check found that an unauthenticated non-JSON request
  attempted Laravel's nonexistent web `login` route. The API now explicitly
  disables guest redirection, returning 401 consistently instead of 500; a
  regression test covers the exact request shape.

## Verification state

- Unknown and inaccessible slugs return the same production 404 response;
  removed memberships also fail as 404, while an active out-of-role member
  receives 403 only after successful tenant resolution.
- Cross-Family-Space invitation and membership identifiers return 404 without
  mutating the resource, and request tenant context is empty after dispatch.
- Backend formatting and PHPStan pass; 55 Laravel tests pass with 348
  assertions, while the existing PostgreSQL-only deferred-trigger test is
  skipped by the normal SQLite suite.
- Frontend formatting, ESLint, strict TypeScript, 26 tests across 12 files and
  the production build pass. npm audit reports no known vulnerabilities.
- The rebuilt web tenant route returns 200, the scoped API route returns 401
  without a session, and the retired global invitation route returns 404.
- Foundation, documentation, Compose, formatting, lint, type, contract,
  dependency-security, infrastructure-smoke and observability-smoke gates pass
  after the live unauthenticated-route correction.

## Existing frontend navigation debt left outside scope

The touched application shell and account/auth navigation now use React Router.
Existing full-page redirects remain in `AccountSecurityPanel`,
`InvitationAcceptanceForm` and `TwoFactorChallengePage`; those security flows
were not otherwise modified by S03 and were not silently folded into this
tenant-routing stage. The invitation acceptance page's one-shot
`history.replaceState` call is the accepted ADR-0004 token-removal mechanism,
not ordinary application navigation.
