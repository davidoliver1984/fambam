# FPA-P03-S05 — Tenancy audit and deletion foundations

**Date:** 2026-08-04

**Status:** Completed — implementation, persistent migration, independent
review follow-up and full Phase 3 gate passed

**ADR:** ADR-0005 §§10–12

## Scope

This final Phase 3 stage completes tenant-aware audit records, asynchronous
tenant propagation, safe storage-key partitioning and the Family Space deletion
state-machine foundation. It does not add Phase 5 media operations, speculative
image-analysis product messages or frontend deletion UI.

## Implementation

- Added Family Space, actor, correlation and W3C trace fields to audit events.
  New trace and correlation fields are non-null; historical rows recover Family
  Space identity from metadata or their subject where possible and receive
  explicit legacy propagation identifiers.
- Kept audit runtime access insert-only under forced RLS. The runtime role has
  no `SELECT`, `UPDATE` or `DELETE` table privileges and no corresponding
  policies. A cast-aware plain insert avoids weakening the policy merely to
  support an unused PostgreSQL `RETURNING` identifier.
- Added `TenantOperationContext` as the exact serializable queue contract and
  propagated it through scheduler producer spans, Laravel job payloads,
  consumer spans, logging, database context and completion audit writes.
- Added Owner-only request/cancel deletion endpoints, Administrator-or-Owner
  pending status visibility, a configuration-driven absolute grace deadline,
  bounded due-work discovery and an idempotent two-step teardown.
- Teardown first claims `deleting`, then marks the Family Space `deleted`
  before soft-removing active memberships in the same transaction. A retry can
  resume `deleting`; stale jobs after cancellation and repeated jobs after
  completion are no-ops.
- Added a separate `fambam-jobs` SQS queue, idempotent LocalStack provisioner,
  queue worker and scheduler services. The Python image-analysis queues remain
  isolated from Laravel jobs.
- Added traversal-safe `families/{family_space_id}/...` storage keys without
  pulling a future media domain into Phase 3.
- Corrected first-account bootstrap so fresh post-RLS installations establish
  their authoritative actor and Family Space database context before creating
  the initial tenant and audit rows.

## Persistent local migration verification

After explicit approval, Compose applied the S05 migration as batch 8 and
rebuilt the API, scheduler and queue worker. Verification established:

- all eight historical audit rows have non-null correlation and W3C trace
  fields; the two recoverable historical tenant events received Family Space
  attribution and platform/account events correctly remain tenant-null;
- audit RLS is enabled and forced with only the intended runtime insert policy;
  the live `fambam_app` role has no read/update/delete privileges or policies
  but successfully performed rolled-back platform and tenant-context inserts;
- the bounded due-deletion function is security-definer, executable by the
  runtime role and returned no work against the real archive;
- the existing Family Space, two memberships, active Owner and invitation
  scoping were preserved;
- the queue worker and scheduler are running, `fambam-jobs` is isolated and
  empty after successful context-complete no-op jobs, and no audit rows or
  archive data were added by verification;
- API health returned 200 and unauthenticated deletion returned 401;
- infrastructure and observability smoke checks passed against the rebuilt
  stack.

The final review follow-up closed the ADR's remaining committed-test-proof
gaps. Two processes concurrently attempted to reactivate one removed
membership; exactly one succeeded and one active row remained. A user with
legitimate memberships in two Family Spaces could not use one tenant context to
mutate the other space's registry, membership or audit data. The pending S05
migration now explicitly revokes audit read/update/delete privileges, and the
persistent database was brought into parity and verified. Frontend regressions
prove unauthenticated tenant-route protection, cache separation while switching
Family Spaces and graceful transition to the indistinguishable 404 state after
membership loss. The complete final gate passed with React 29/29, Laravel 60
passed plus the separately executed PostgreSQL 11/11, and Python 4/4.

The first rebuilt smoke run exposed a raw smoke payload still being sent to the
new Laravel jobs queue. The worker rejected that malformed historical test
shape three times as configured. The smoke now dispatches the real
context-complete no-op Laravel job; a clean worker restart and repeated smoke
confirmed successful processing with no recurrence and no queue purge.
