# FPA-P07-S05 — Event notifications and exports

## Outcome

Phase 7 now notifies the live Event cohort when a newly uploaded contribution
first becomes available and lets an Owner or Administrator request a curated,
short-lived Event archive. Archive generation preserves original bytes, verifies
their checksums and records useful metadata without extending Guest authority.

## Implementation

- Added one queued, retry-safe contribution notification after the first
  successful Event Album finalisation. Recipient selection is evaluated live,
  deduplicated and excludes the uploader, removed memberships, revoked accounts
  and expired or revoked admissions.
- Added tenant-owned `EventExport` records with forced PostgreSQL RLS and the
  `pending`, `processing`, `ready`, `failed` and `expired` lifecycle.
- Added bounded, overlap-protected background generation of deterministic ZIP
  archives containing one untouched preserved original per distinct Event Photo
  plus a schema-versioned JSON metadata manifest.
- Added checksum validation, fail-closed missing-object handling, five-minute
  signed-download authorization, 24-hour retention and hourly idempotent expiry
  cleanup.
- Integrated Event exports into audit recording, Family Space teardown and the
  tenant-scoped storage cleanup boundary.
- Added typed feature-local Event API functions, query keys and TanStack Query
  hooks. The Event page shows accessible archive controls only when the API
  reports management authority.
- Reconciled the Implementation Guide with the notification cohort, archive
  format, authorization, lifetime and worker-operational decisions required by
  ADR-0009 before implementation.
- Closed the independent Phase 7 review findings: Guest-created Photos now
  remain governed by live Event access; simultaneous new-account Event
  invitation acceptance is serialized and reuses one Guest membership; Event
  Album detachment resets Guest participation; Event update date ranges are
  validated consistently; `event_admissions` has direct RLS proof; and a
  tenant-scoped delivery ledger prevents successful recipients being mailed
  again after a partial notification failure.

## Architecture

No accepted ADR text required correction. The implementation follows ADR-0009
and does not introduce notification preferences, anonymous contributions,
general Guest access, partial archives or an assertion that Laravel observed the
signed object-store GET.
