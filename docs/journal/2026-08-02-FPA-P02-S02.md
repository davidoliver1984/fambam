## How the system works

The React client first requests Sanctum's CSRF cookie, then sends credentialed
requests to Fortify's headless endpoints. Laravel stores authenticated sessions
in PostgreSQL and protects authenticated API routes with `auth:sanctum`.
Password-reset links target the React application, while both known and unknown
email addresses receive the same external reset-request response.

Fortify's registration feature and route are disabled. Its user-creation action
also fails closed as defence in depth; FPA-P02-S03 will provide the only HTTP
account-creation path through validated invitations.

## What I learned

### Laravel and software engineering

Laravel's `shouldRenderJsonWhen` callback replaces the framework default rather
than extending it. It must preserve `expectsJson()` for Fortify endpoints at the
web root as well as identifying `/api/*`, otherwise SPA validation failures are
rendered as browser redirects.

### Python and image analysis

No Python image-analysis behaviour changed in this stage.

### Security, privacy and operations

Fortify's default failed password-reset-link response reveals an unknown email
through a 422 validation response. A narrowly bound response maps that case to
the same generic success shape as a known email. Cookies remain HTTP-only and
SameSite=Lax; secure-cookie settings are explicit per environment.

## Decisions

- Add the accepted TOTP schema now, but do not enable MFA before FPA-P02-S04.
- Keep password-policy hardening and global revocation within FPA-P02-S04 as
